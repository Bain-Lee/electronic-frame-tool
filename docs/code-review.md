## 已修复问题

### P2 校验正确的错误结束帧被弱候选遮蔽

位置：`src/FrameTools/FrameStream.cs` 中候选优先级。

输入以下 645 报文时，CS 为正确的 `C4`，但结束符被改为 `00`：

```text
68 12 00 00 00 00 00 68 11 04 33 33 34 33 C4 00
```

旧版本将它显示为本地协议的未完整候选。继续拼接正常的本地报文后，错误候选还可能覆盖下一条报文的头部，使下一条报文不能独立显示。

修复：完整、结束符及 CS 均匹配的候选仍最优先；随后优先处理完整且 CS 匹配的候选，再考虑仅结束符匹配或未完整的弱候选。多个同等有效候选仍保留歧义，不强行选定规约。

新增两项回归：单独的损坏结束符 645 必须给出错误帧诊断；它后接正常本地帧时，两条均应独立保留和解析。两项在修复前均失败，修复后通过。

### P2 业务输入框截断合法大报文

位置：`src/FrameTools/MainForm.cs` 的 `ConfigureHex` 及组帧业务输入。

旧版本仅放宽原始输入框的字符上限，组帧业务输入框仍使用默认的 32767 字符。合法上行业务区最多可以有 16373 字节，带空格 HEX 需要 49118 字符，因此用户编辑 / 粘贴的业务数据可能在协议最大长度之前被截断。通过 `.Text` 直接赋值会绕过原生输入限制，原有代码流程测试没有覆盖该路径。

修复：在既有 HEX 文本框配置方法中统一放宽字符上限。报文长度仍由原有的三协议组帧函数约束，没有增加新的校验层或改变长度规则。

补充原生输入路径回归，验证超过 32767 字符且处于协议长度范围内的业务 HEX 可以完整输入。
