# 电力报文工具功能与技术设计

版本：0.3.0。日期：2026-10-28。

## 目标与首版范围

在同一个 Windows 工具中完成“粘贴报文 → 自动识别和分帧 → 定位字段 → 解释结构 → 修改参数 → 生成报文 → 再解析检查”的工作。当前使用场景按离线开发、协议学习和联调前准备处理。

首版实现三种协议的帧结构和通用组帧，保留完整原始数据。业务数据逐项扩展，避免将尚未核对的数据内容解释成确定结果。首版不是覆盖全部附录的数据字典，也不是完整主站或电表模拟器。

0.2.0 增加自动识别、有空格 / 无空格兼容、连续多帧整形和逐条解析。自动识别范围仍限定为本机标准对应的三种规约，不据此支持参考项目的全部协议。

0.3.0 按使用反馈将识别触发改为明确点击：启动不加载样例、不解析，输入、追加、示例和文件载入也不解析。自动识别开关仅选择匹配策略。协议核心、连续分帧规则和组帧规则保持不变。

## 标准基线

| 协议 | 本机依据 | 对实现的直接约束 |
| --- | --- | --- |
| 645 | DL/T 645-2007，第 5～7 章及附录 A | 6 字节 BCD 地址，双 68，数据域 ±33H，DI0 先传；读长度不超过 200、写长度不超过 50 |
| 南网本地 | 本地通信模块接口协议（试行），第 5～6 章 | L 是整帧总长度；ADD 决定 12 字节地址域；SEQ 是 0～255 的完整序号；DI 为 4 字节 |
| 南网上行 | 上行通信规约 2024版V2.0，封面 2026年8月，第 5 章、6.1、6.2 | 两个相同的直接 BIN 长度 L；7 字节地址；SEQ 含位标志；DA 为 2 字节，DI 为 4 字节；PW、Tp 有各自条件 |

原始路径见 [标准清单](../specifications/README.md)。本地标准的确切独立版次暂不自行命名。MQTT 文件存在，但没有据此假定 MQTT Topic、Payload 封装或业务参数。

### 帧格式

| 协议 | 传输结构 | 长度规则 | CS 计算范围 |
| --- | --- | --- | --- |
| 645 | `[FE…] 68 A(6) 68 C L DATA(L) CS 16` | 帧长 `L+12`，不含 FE | 从第一个 68 到 DATA 最后字节，模 256 累加 |
| 本地 | `68 L(2) C [ASRC(6) ADST(6)] AFN SEQ DI(4) DATA CS 16` | L 为总帧长；含两个长度字节 | 从 C 到业务区末尾，模 256 累加 |
| 上行 | `[FE…] 68 L(2) L(2) 68 C A(7) AFN SEQ APP CS 16` | L 是 C、A、应用层的总字节数；帧长 `L+8` | 从 C 到应用层末尾，模 256 累加 |

多字节长度低字节先传。南网上行的 L **不使用**国网规约中的长度左移两位再附标志的编码。本地和上行报文也不整体执行 645 的 ±33H。

上行地址由 A1（3 字节 BCD 省地市区县码）、A2（3 字节 BIN 终端地址）、A3（1 字节主站地址）组成。界面明确按传输顺序输入，避免把 7 字节地址当成单个 BCD 表地址。

本地 ADD 在 C 的 D5；上行 C 的 D5 是 FCB/ACD。本地 SEQ 与上行 SEQ 的语义也不同。代码分别处理这些字段。

## 界面与交互

顶部提供规约选择和默认勾选的“自动识别规约”，主体分为“报文解析”和“组装报文”两页。解析页勾选自动时禁用手动规约选择；每条报文的匹配结果单独显示。关闭自动后按手选规约处理。组帧页隐藏开关、恢复下拉框可用并将标签改为“组帧规约”，组帧功能不被自动解析模式锁定。

解析页上方输入原始 HEX，下方为自动整形区、逐条选择、整体统计、字段表和诊断说明。原始输入不被改写，整形区按字节加空格、按报文分行。字段表偏移从每条报文的 0 开始；来源偏移是完整输入中的字节位置，均包含相应 FE。点击字段会选中整形区的准确字节。

输入或解析模式变化会清除过期结果，直到用户点击“识别并解析”或按 Ctrl+Enter 才处理。启动不载入请求示例；载入示例、打开文件、生成结果送入解析页都只填充输入。末尾单个十六进制字符作为半字节保留，追加后再次点击识别即可补全。报告导出包含所有已分帧结果、待定片段和末尾半字节；未识别时导出按钮禁用，不通过导出操作隐式解析。

界面以 iOS 的分组、留白、主次层级为参考，使用浅灰底、白色输入面、系统蓝主按钮和原生控件的轻量绘制。代码编辑区保留等宽字体，字段表保持清晰的行分隔和字节定位。小窗口组帧页采用滚动，避免业务区被参数区挤压。

组帧页按协议启用相关参数。645 的 DI 单独填写，后续明文字节放在业务区；本地地址只在 ADD=1 时启用；上行的完整应用区按传输顺序填写。参数改动会清除旧生成结果，防止复制过期报文。生成结果可以送回解析页检查结构。

解析页明确区分两件事：

- **结构检查**：当前输入能否满足已实现的起止、长度、校验等约束。
- **业务解释范围**：哪些字段已解释，哪些内容仅保留原始数据，哪些需要认证信息或真实设备才能验证。

字节输入不能反映串口的起始位、停止位、偶校验位或实际时序，因此离线工具不声称验证物理层通信质量。

### 自动识别和连续分帧

首先归一化既有 HEX 分隔符，保留完整字节及末尾半字节，再按三种规约分别探测头部和声明长度。完整且校验通过的候选优先；若有多个有效候选，显示歧义并要求手动选择，不默认回落为南网。本地规约不接受前导 FE，因此帧前 FE 单独保留。

只按长度域确定报文边界，不按业务区出现的 `68` / `16` 切开。完整外层的结束符或 CS 仍可支持其边界时，保留外层及错误诊断，不将业务区内嵌的合法 645 提升为独立报文。对结构已不成立的区域，可以在后续校验通过的边界重新定位，前面的字节仍作为待定片段保留。

若一个可能的外层报文只是尚未输入完整，则保留其整个尾部等待后续字节。声明长度被损坏但恰好落在后面的 `16` 上，与真实外层数据可能无法区分；这种情况保留声明范围和错误，不声称能够唯一恢复。纯 HEX 输入没有额外的日志边界信息，不能消除所有歧义。

输入接口不自动删除任意非 HEX 文本。带时间戳、收发标签的完整设备日志暂不自动抽取，避免将文字中的 A～F 和时间数字混进报文。

## 当前业务解析边界

### 645

解释地址、方向、功能、异常标志、后续帧标志、长度、±33H 还原和适用命令中的 DI。对普通读数据应答中 DI=`00010000` 的 4 字节 BCD 值显示 kWh，对 DI=`02010100` / `02010200` / `02010300` 的 2 字节 BCD 值显示 V。数据长度不同或含无效 BCD 时只给说明，不强行换算。

读后续数据、写数据等功能可以在帧结构层查看和封装，但没有完整解释各自的密码、操作者代码、序号与全部业务参数。用户需要自行按标准准备业务数据。

### 南网本地

解释可选源 / 目的地址、控制位、AFN、8 位 SEQ、4 字节 DI，并显示数据标识内容原始值。DI1 与 AFN 不一致时给出版本 / 协议核对提示。暂不完整解码任务、节点档案、文件传输和模块运行参数。

### 南网上行

解释链路头、7 字节地址、控制位、AFN、SEQ 位域和由 TpV 明确标识的 5 字节时间标签。对已核对明文布局的 AFN `00`、`02`、`0A`、`0C`，提供首个 DA、DI 的辅助视图。DA 支持 p0、多位测量点和全部测量点标识。

应用业务区始终保留原始值，不把整个业务区当成固定长度数据项。加密写参数等报文不自动解释为明文 DA、DI；PW 及多信息体边界暂不自动推断。Tp 仅分界显示，不验证时效。

## 技术方案

首版采用 **C# 5 / .NET Framework 4.8 / WinForms**。原因是当前交付目标限定 Windows，系统组件足以实现界面和协议运算，可以直接生成小体积 EXE，避免增加包管理和第三方运行时。运行机器仍需要安装 .NET Framework 4.8。

代码只划分必要职责：

| 文件 | 职责 |
| --- | --- |
| `src/FrameTools/Protocol.cs` | HEX 处理、三协议解析、帧字段结果及三种组帧函数 |
| `src/FrameTools/FrameStream.cs` | 三协议自动匹配、长度分帧、未完整 / 歧义片段保留及整形结果 |
| `src/FrameTools/MainForm.cs` | 参数输入、字段显示、定位、导入和导出 |
| `src/FrameTools/WorkspaceStyle.cs` | 按钮、开关、分段页签的绘制；保留原生控件基类和键盘语义 |
| `src/FrameTools/Program.cs` | Windows 程序入口和版本信息 |
| `tests/ProtocolTests.cs` | 固定报文、边界 / 错误输入、窗口构造测试 |
| `tests/StreamTests.cs` | 混合连续流、空格兼容、半帧 / 半字节、嵌套保护和真实规约歧义 |
| `tests/WindowFlowTests.cs` | 通过窗体控件和消息循环验证自动输入解析、逐条选择、高亮与持续追加 |
| `Build.ps1` | 本机构建及测试，不安装全局依赖 |

当前不引入插件框架、数据库、网络服务、自动更新或动态脚本。业务字典需要扩展时，再根据真实数据项的重复结构决定配置格式。若后续出现明确的界面或运行时需求，再评估 WPF / 更新版 .NET 的迁移成本。

## Windows 交付

交付 `artifacts/FrameTools.exe`，由本地构建脚本重现。程序不需要管理员权限，不需要联网，不需要安装 Python。原始标准和临时摘录不打包进 EXE。

本次只在当前 Windows 机器验证编译、测试和启动情况；不能据此声称已在所有 Windows 10 / 11 版本、DPI 或真实设备上完成验收。当前未做安装包和代码签名。

## Git 方案

本地使用 `main`。源码、文档、测试和构造样例纳入 Git；原始标准、临时文件及 EXE 构建产物排除。原始标准仍保留在原目录，不移动或删除。

后续单项功能用短期功能分支开发，通过相关测试再合并。版本号写入程序和文档，稳定交付后用版本标签定位。远程仓库为 [Bain-Lee/electronic-frame-tool](https://github.com/Bain-Lee/electronic-frame-tool)，同步源码、测试、示例和文档；原始标准、临时摘录和构建产物保持排除。

## 验收条件与后续证据

首版验收项：三协议固定样例解析成功；组帧与独立固定向量逐字节一致；645 ±33H 及 FE 校验范围正确；本地 ADD 和 8 位 SEQ 正确；上行直接 BIN 长度、重复长度和 7 字节地址正确；错误及截断输入可诊断；EXE 可构建、窗口初始化不抛异常。

下一阶段还需要每个协议的真实请求 / 应答对，以及业务预期值。优先包括带地址 / 不带地址的本地报文、多信息体的上行报文、带 Tp / PW 的报文，以及 645 的普通、后续和异常应答。抓包样本用于验证具体行为，构造样例不替代设备联调。
